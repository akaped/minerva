# Minerva API v1

Base URL: `/api/v1`. JSON request/response bodies. Errors are `{"error":"message"}` with an appropriate HTTP status. Request bodies are limited to 2 MiB. GET endpoints are read-only. All other methods require `X-Minerva-Client: 1`, including login. Unknown routes return 404.

## Authentication

`POST /login` accepts `{ "email": "...", "password": "..." }` and returns `{ "user": {...}, "token": "..." }`. Browser sessions use the HttpOnly, SameSite=Strict `minerva_session` cookie. Native clients can send `Authorization: Bearer <token>`. Tokens expire after seven days; only their SHA-256 hashes are persisted. `POST /logout` revokes the presented token and clears the cookie.

Use HTTPS for remote clients. `MINERVA_SECURE_COOKIE=1` enables the cookie's Secure flag. CORS is not enabled; browser clients are served from the same origin. The custom mutation header and JSON body prevent ordinary cross-site form submissions. Authentication tokens must never be placed in URLs.

## Save contract

```json
{
  "title": "A useful thought",
  "icon": "✳",
  "revision": 3,
  "favorite": false,
  "trashed": false,
  "archived": false,
  "blocks": [
    {
      "id": "stable-unique-block-id",
      "markdown": "## Hello",
      "x": 40.0,
      "y": 40.0
    }
  ]
}
```

`cover` (optional) is empty, `gradient:1`–`gradient:8`, `/api/v1/attachments/{id}`, or an HTTPS URL of at most 500 bytes. `tags` (optional) holds up to 20 tags, normalized to lowercase without `#`, each 1–40 letters, digits, `-`, `_`, or `/` with at least one letter. Inline `#tags` in block text are derived and returned as `inline_tags`. Links to other notes use the Markdown destination `#note/{id}`; guests and published pages receive their text without the link.

The note's folder is immutable through this endpoint. The server increments the revision after a successful save and returns the updated note. Maximum 2,000 blocks, 100,000 bytes per block, title 1–200 bytes, icon at most 24 bytes, unique nonempty block IDs at most 80 bytes, and finite coordinates within ±100,000. Overall request-size limit applies too. Names and titles should be kept short; server limits are UTF-8 byte lengths.

HTTP 409 means another client saved first. Preserve/export the local draft, fetch the latest note, and explicitly reconcile before retrying. Do not automatically overwrite the new revision with the old payload. To restore history, submit a previous snapshot's content with the **current** note revision. Trash/restore uses the same PUT with `trashed` toggled; no permanent deletion endpoint exists. Archiving also uses it, with `archived` toggled: an archived note keeps its folder and access but is left out of search, the graph, and AI answers about a folder or workspace.

Authorization is evaluated against current state on every request. Treat 401 as requiring sign-in and 403 as loss of permission. The server uses a stable UUID per database; future clients should namespace cached entities by that UUID. API v1 supports independently authenticated servers and live CRDT note synchronization, and a WebSocket change feed (below), but no federation, attachment transfer, or durable offline synchronization.

## Live collaboration

`POST /notes/{id}/sync` accepts `{update?, state_vector?, client_id?, active_block?, editing?, leave?}`. The reply's `update` holds the whole document, or with `state_vector` (the client's base64 Yjs state vector, v1) only what the client lacks. `editing: true` claims `active_block` for editing; only one client holds a block, and a later claim is refused. `leave: true` removes the client's presence at once. `update` is a base64 Yjs update-v1 message; omission/empty string performs read synchronization and a presence heartbeat. Read synchronization requires folder read access. Nonempty updates require editor access. Body limits still apply, and malformed or oversized CRDT updates are rejected.

Response: `{update, note, peers, can_edit, denied_block}`. `denied_block` names the block this client asked to edit while another client held it; the client should close its editor for that block. `update` contains the merged encoded document state; `note` contains the validated canonical projection and sanitized rendered HTML. `peers` contains user ID, display name, per-tab client ID, active block, whether that block is open for editing, and heartbeat timestamp. Presence expires after 10 seconds and is permission-filtered. Duplicate CRDT updates are idempotent. The browser sends pending changes after a 180 ms debounce, syncs when the change feed signals, and polls every 5 s (650 ms without the feed). Full CRDT states are returned.

`GET /api/v1/live` upgrades to a WebSocket for signed-in pages of the same origin (other `Origin` headers get 403). Send `{"watch": [note IDs]}` (up to 32; each message replaces the list); the server sends `{"note": id}` when a watched note's content, details, or presence changed. Signals contain no content and are only sent while the reader can still open the note; then call `POST /notes/{id}/sync`. Pages that cannot open a socket (the desktop app's, whose requests its gateway forwards) call `GET /live/wait?notes=a,b` instead: it answers `{notes: [ids]}` as soon as one of them changes, or `{notes: []}` after 25 seconds, and the page asks again. Share-link guests open `GET /api/v1/shared/live` (with their share cookie), which watches only the shared note.

Yjs/Yrs roots: `title` text; `order` string-ID array; `block:<id>` text; `meta` map with `icon` string, `favorite` boolean, `trashed` boolean, `archived` boolean, and optional `cover` string and `tags` string array (validated as for saves). Folder IDs, user roles, and identity are not editable through CRDT payloads. Limits: 2,000 materialized blocks, 100,000 bytes per block, 200-byte title, 24-byte icon, encoded incoming update 1.5 MB, stored encoded state 2.5 MB. Exceeding a limit rejects the update and keeps the client's unsaved changes for export/recovery.

## Graph

`GET /workspaces/{id}/graph` returns `{nodes, links}` for the graph view: `nodes` are the workspace's notes the caller can open (not trashed or archived), each `{id, title, icon, folder_id, updated_at, tags, journal, record}` (`tags` includes inline `#tags`), and `links` are `[from, to]` pairs of note IDs, one per linking note and target, for links written as `[…](#note/{id})`, links to a block (`#note/{id}#{block}`) and embeds (`![…](#note/{id})`). A link to a note the caller cannot open is left out. 403 when the caller can open nothing in the workspace. The response also has `positions`, `{id: [x, y]}`: where the caller placed notes (or tag nodes, `#tag`) by dragging them.

`PUT /workspaces/{id}/graph/positions` keeps those positions for the caller: `{positions: {id: [x, y] | null}}` places the nodes named (`null` lets one move freely again) and keeps the others; `{reset: true}` releases them all. Up to 5,000 positions per person and workspace; coordinates are finite numbers within ±1,000,000.

## Languages

`PUT /account/language` with `{language}` (`en` or `it`) records the language the caller reads the app in; the app sends it when it starts. Emails to the person are written in it. Published pages use the visitor's `Accept-Language`, and exports the exporting person's language. Error messages (`error` in responses) are always English: the app translates them with the same catalog (`web/locales/`).

## Embedded notes and blocks

In Markdown, `[text](#note/{id}#{block})` links to a block, and `![text](#note/{id})` or `![text](#note/{id}#{block})` embeds a note or a block. Rendered for members, an embed is an empty `<span class="note-embed ne-note-{id} ne-block-{block}">` slot; for share-link guests and published pages, a short note.

`POST /embeds` with `{items: [{note, block?, revision?}]}` (at most 50) returns, in order, `{note, block, state, title?, icon?, revision?, can_edit?, blocks?, more?, unchanged?}` for each (each block `{id, html, markdown}`; `can_edit` when the caller edits the note):

- `state` is `ok`, `trashed`, `no-block` (the note no longer has the block), or `unavailable` (the note does not exist or the caller cannot open it; nothing else is returned then).
- `blocks` is `[{id, html}]`: the block and the blocks nested under it (their indentation counted from the block), or every block of the note, up to 300 (`more` is true when there are more).
- When `revision` is the note's current revision, the item comes back `unchanged: true` without `blocks`, so a client can check for changes cheaply.

400 for a malformed note ID or block ID, or more than 50 items.

## Structured databases

| Method | Path                                 | Contract                                                                                                                                                                                          |
| ------ | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| POST   | `/databases`                         | `{folder_id,name,columns?}`; creates default Name/Status columns if omitted                                                                                                                       |
| GET    | `/databases/{id}`                    | Complete schema and records; folder read permission required. Each record carries `computed` (rollup and formula values by property ID), and `page` (its page's note ID) when it has one          |
| PATCH  | `/databases/{id}`                    | `{revision,name?,columns?}`; matching schema revision and folder editor permission. Values that no longer fit the new schema (a removed property or select option, or a changed type) are cleared |
| DELETE | `/databases/{id}`                    | Folder editor; deletes the database and its records permanently                                                                                                                                   |
| POST   | `/databases/{id}/rows`               | `{cells:{property_id:value}}`; returns record with revision 1                                                                                                                                     |
| PATCH  | `/databases/{id}/rows/{row_id}`      | `{revision,cells?,archived?}`; merges only supplied cells, increments row revision                                                                                                                |
| DELETE | `/databases/{id}/rows/{row_id}`      | Folder editor; deletes the record permanently (archiving is the recoverable option), with its page                                                                                                |
| POST   | `/databases/{id}/rows/{row_id}/page` | Folder editor; `{id}` of the record's page, made the first time (or taken out of the trash)                                                                                                       |

Column shape: `{id,name,kind,options?,target?,rollup?,formula?}` where kind is `text`, `number`, `checkbox`, `date`, `select`, `multi_select`, `url`, `person`, `relation`, `created`, `edited`, `rollup`, or `formula`. Null/missing cells are allowed. Dates must be real calendar dates in YYYY-MM-DD form. Select values must be in the property's declared options; a multi-select value is a list of distinct options (removing an option takes it out of records and keeps the rest). A person value is a member's user ID; `GET /databases/{id}/people` lists the members who can open the database (`{id,name}`). A relation names its `target` database, which must be in the same workspace and readable by whoever sets it; its value is a list of up to 100 record IDs. `created` and `edited` show each record's `created_at` (set by the server; 0 for records from before it was kept) and `updated_at`, and cannot be written. URLs must start with HTTP(S); values are displayed as text inputs, not trusted HTML. Schemas support 1–32 columns and databases up to 10,000 records. Schema changes clear the values they make invalid instead of being rejected; each cleared record's revision increases. The UI can add, edit (name, type, options), and delete properties, rename and delete databases, and archive or delete records.

**Rollups and formulas** are computed when a database is read, for the reader, and cannot be written.

- A rollup is `{"relation": <relation property ID>, "property": <property ID in the related database>, "function": …}`. `function` is `count` (records linked; `property` may be empty), `count_values`, `sum`, `average`, `min`, `max`, `earliest`, `latest` (dates) or `list`. The property cannot be a relation, rollup or formula. A reader who cannot open the related database gets `null`.
- A formula is an expression of up to 1,000 characters: properties as `prop("Name")` (case-insensitive; renaming a property updates formulas), numbers, `"text"`, `true`/`false`, `+ - * / %` (`+` joins text), comparisons (`== != < <= > >=`, and `=`), `and`/`or`/`not` (`&& || !`), and the functions `if(c, a, b)`, `concat(…)`, `join(list, sep)`, `length`, `contains`, `lower`, `upper`, `empty`, `round(x, digits?)`, `floor`, `ceil`, `abs`, `min(…)`, `max(…)`, `today()`, `days(from, to)`, `add_days(date, n)`, `year` and `month`.
- Formulas see people and related records by name, dates as `YYYY-MM-DD`, and other formulas and rollups. A value that does not fit (text times a number, division by zero, a formula that refers to itself) is `null`. Saving a schema with a formula that does not parse, or that names a missing property, returns 400 with the reason.

**Record pages.** A record can open as a page: a note in the database's folder with `record: {database_id, record_id}`, also in `/bootstrap` summaries. The app lists it with its record, not with the folder's notes. Its title is always the record's name (the first property): saves keep it, and renaming the record renames the page. It cannot be moved to another folder, and it is deleted with its record or database.

**Databases in notes.** A block containing `[[database:{id}]]` (or `[[database:{id}:board]]`, `[[database:{id}:calendar]]`) shows that database inside the note. A board or calendar can name the property it groups or places records by: `[[database:{id}:board:{property id}]]`; without one, the first that fits is used. For signed-in members the server renders `<span class="db-embed db-id-{id} db-view-{view}">`, which the app fills with the current records using the normal database endpoints, so folder permissions apply: readers without access see a notice, viewers see it read only, and editors can edit cells and add records in place. The view refreshes every few seconds. Share-link guests and published pages only see a short placeholder, never the records. Exports (Markdown, HTML, PDF, ZIP) include a snapshot table when the exporting member can read the database. In the editor, type `/` and choose **Database (live)**, or copy the code from the database page with **Use in a note**.

Records use optimistic concurrency. Local browser writes are serialized, but stale writes from other clients return 409 rather than overwriting their changes. Archiving is recoverable; no permanent deletion route is exposed. Database metadata is included in `/bootstrap`, filtered by current folder permissions.

## Personal API tokens

For scripts and `minerva-cli`. A token signs in as its owner with `Authorization: Bearer mnv_api_v1_…` and has the owner's permissions on every API, export and attachment route, but cannot manage the account: `api-tokens`, `mcp-credentials`, `account/*` (password, second factor) and `logout` answer 403. Server administrator accounts cannot create tokens. Only SHA-256 hashes are kept. A token created with `access: "read_only"` may only read: any method but GET (and `POST /search`) answers 403, on every route.

| Method | Path               | Contract                                                                                                                                                  |
| ------ | ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api-tokens`      | Your tokens: `{id, name, access, created_at, expires_at, last_used_at}` (`last_used_at` recorded at most once a minute, `null` if never); never the token |
| POST   | `/api-tokens`      | `{name, expires_days?, access?}`: 1–80 character name, 1–365 days (default 90), `read_write` (default) or `read_only`; returns `token` once; up to 20     |
| DELETE | `/api-tokens/{id}` | Revokes one of your tokens at once                                                                                                                        |

`POST /notes/{id}/append` with `{markdown, after_block_id?}` adds Markdown to a note as blocks, at the end or after a block, like an edit in the app (the previous version goes to history, open editors update). Editor access; returns the note with `added_block_ids`.

### `minerva-cli`

Each release has it for Linux and Windows (`minerva-cli-…` downloads), or build it from `crates/minerva-cli` (`cargo build --release -p minerva-cli`; `scripts/package-cli.sh` makes the packages). Set `MINERVA_URL` and `MINERVA_TOKEN` (a read-only token is enough for `search`, `folders` and `backup`), then:

```sh
minerva-cli search budget review          # ID, title and snippet of each match
minerva-cli folders                       # folder IDs and paths
echo "- call the bank" | minerva-cli new "Inbox" "Monday"   # folder by name, path or ID
minerva-cli append NOTE_ID "One more thing"
minerva-cli backup ./backup [--files] [--full]   # notes as Markdown (or zips with attachments), databases as JSON
```

`backup` keeps `.minerva-backup.json` in the folder: the next run fetches only notes and databases changed since (by their last change), writes a renamed or moved one to its new place and removes its old file, and keeps files of notes deleted since. `--full`, or switching between Markdown and `--files`, fetches everything again.

### Note attachments

- `POST /api/v1/notes/{id}/attachments?filename={URL-encoded-name}` accepts raw bytes with `X-Minerva-Client: 1`, a login session, and folder editor access. Returns 201 with `id`, sanitized `filename`, `media_type`, and `size`. Trashed notes reject new uploads.
- `GET /api/v1/notes/{id}/attachments` lists all retained uploads for an accessible note, including files no longer referenced by current blocks.
- `GET /api/v1/attachments/{id}` downloads the original bytes with attachment disposition and an encoded filename.
- `GET /api/v1/attachments/{id}/preview` displays signature-identified PNG/JPEG/GIF/WebP images only. Other formats, including SVG and HTML, are download-only. Signature detection is not full image validation or malware scanning.

Current folder permissions are checked on every operation. Login credentials work; MCP tokens do not authorize these endpoints. Files use UUID primary keys in a separate SQLite blob table, never uploaded filesystem names. `/preview` serves images, audio and PDFs inline (PDF responses may be framed by Minerva's own pages, for the tab beside the note); other files only download. Limits: 60 MiB per upload, 500 MiB per note, and 10 GiB per server by default (`MINERVA_ATTACHMENT_STORAGE_GB`). Uploads and note edits are separate operations; interrupted insertions can be recovered from the note's Files dialog. No automatic deletion: retained blobs protect history and can be reinserted. Future administrator cleanup must account for revision and share references.

Markdown images support HTTP/HTTPS image URLs and uploaded attachment URLs, for example `![Photo](/api/v1/attachments/{id})`; image destinations are automatically rendered through `/preview`. Regular Markdown links still download originals. External images are fetched directly by the browser, not proxied by the Rust server. HTTPS deployments remain subject to browser mixed-content restrictions for HTTP images. Server filesystem paths are not public URLs; upload the file and use its attachment URL.

Only folder-level editors (folder editors, workspace owners, administrators) manage sharing. See `sharing.md` for the model.

## Journals and templates

Each workspace can have one Journal folder and one Templates folder. A workspace owner creates them the first time journals or templates are used. After that, access follows normal folder permissions. `bootstrap` returns `journal_folders`, `template_folders`, and `journal_templates` (workspace ID → folder or note ID). Journal entries carry `journal: "YYYY-MM-DD"` on the note.

| Method | Path                      | Contract                                                                                                                                                                                                                                                                                                                  |
| ------ | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| POST   | `/journal`                | `{workspace_id, date}`. Returns the entry for that date, creating it (with the journal template, if set) when missing. `created` tells which. Creating requires editor access to the Journal folder                                                                                                                       |
| PUT    | `/journal/settings`       | `{workspace_id, template_id \| null}`; owners only; the template must be in the workspace's Templates folder                                                                                                                                                                                                              |
| POST   | `/templates`              | `{workspace_id, title}`; creates a template note                                                                                                                                                                                                                                                                          |
| POST   | `/notes/{id}/template`    | `{template_id, date}`. Fills an empty note (409 otherwise) with a copy of the template: new block IDs, `{{date}}`, `{{weekday}}`, `{{long_date}}`, and `{{title}}` replaced; icon, cover, and tags added when the note has none. `date` is the caller's local date; journal entries use their own date                    |

## Reminders

Reminders made on the Reminders page belong to their workspace: everyone who can open it sees them, gets the email when one is due, and everyone who can edit in it (the whole workspace, or one of its folders) can add, change, complete or delete them. `/remindme` reminders stay personal: only the person who set one sees it or gets the email.

| Method | Path                   | Notes                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------ | ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/reminders`           | `{enabled, reminders, from_notes}`. `enabled` is whether the server sends email. `reminders` holds your `/remindme` reminders and the reminders of every workspace you can open, each with `created_by` (a name) and `can_edit`. `from_notes` lists every `⏰YYYY-MM-DD HH:MM` time written in notes you can open, with `note_id`, `block_id`, `workspace_id`, the block `text`, the `stamp` as written (local time), and `emailed` |
| POST   | `/reminders`           | `{workspace_id, title, category?, at, repeat?, offset?}` makes a reminder in a workspace you can edit in. `at` is Unix seconds; `repeat` is `{every: 1–1000, unit: "day"\|"week"\|"month"\|"year"}`; `offset` is minutes east of UTC, so repeats keep the local time and day of the month. `{note_id, block_id, at}` instead emails a block (`/remindme`, needs email)                                                              |
| PUT    | `/reminders/{id}`      | Same fields as creating, without `workspace_id`                                                                                                                                                                                                                                                                                                                                                                                     |
| POST   | `/reminders/{id}/done` | A repeating reminder moves to its next time after now and `{next}` returns it; any other is removed and `next` is `null`                                                                                                                                                                                                                                                                                                            |
| DELETE | `/reminders/{id}`      | Removes it                                                                                                                                                                                                                                                                                                                                                                                                                          |

With email set up, a due workspace reminder is emailed once to everyone in the workspace and stays due until it is marked done. A `/remindme` block is emailed and then forgotten.

## Two-factor authentication

Accounts can require a code from an authenticator app (TOTP, RFC 6238: SHA-1, 6 digits, 30 seconds).

**Sign-in.** When 2FA is on, `POST /login` with a correct password returns `{two_factor_required: true, challenge}` instead of a session. `POST /login/2fa` with `{challenge, code}` returns the usual `{user, token}` and session cookie. `code` is an authenticator code or a recovery code (case and spacing ignored).

- A challenge lasts 5 minutes, is single use, and ends after 5 wrong codes. Wrong codes count even though the request fails.
- Codes are accepted one step either side of the current time, and each code works only once per account.
- Both steps count toward the sign-in rate limit.

| Method | Path                    | Contract                                                                                                                   |
| ------ | ----------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/account/2fa`          | `{enabled, enabled_at, recovery_remaining}`                                                                                |
| POST   | `/account/2fa/setup`    | Starts setup: `{secret, uri, qr_svg}` (`otpauth://` URI and an SVG QR code). Valid for 15 minutes                          |
| POST   | `/account/2fa/enable`   | `{code}` from the app → `{recovery_codes}` (10 single-use codes, shown once). Other sessions of the account are signed out |
| POST   | `/account/2fa/recovery` | `{code}` from the app (not a recovery code) → new `{recovery_codes}`, replacing the old ones                               |
| POST   | `/account/2fa/disable`  | `{password, code}` (authenticator or recovery code)                                                                        |

Administrators see `two_factor` in `GET /admin` users and can reset it with `PATCH /users/{id}` `{two_factor: false}`. Recovery codes are stored as SHA-256 hashes. The TOTP secret is stored in the database, so protect the database file as you would password hashes. The desktop gateway captures the session from `/login/2fa`, and `minerva-client` provides `Transport::login_with_code`.

## Writing actions

`POST /ai/transform` with `{provider_id, action, text, language?}` returns `{text}`: `action` is `improve`, `fix`, `shorter`, `longer`, `translate` (with `language`, letters only) or `continue`. `text` is 1–12,000 bytes and is sent to the provider with that instruction only; nothing is stored. One AI request per user runs at a time.

`POST /import?folder_id=…&name=…` with a file as the body (up to 200 MB; `X-Minerva-Client: 1` required): a zip (Notion, Obsidian, Logseq), an `.enex` (Evernote) or Markdown. ## Comments

`GET /notes/{id}/comments` lists a note's threads: `{id, note_id, block_id, quote, resolved, resolved_by, resolved_by_name, created_at, comments: [{id, author, author_name, mine, text, created_at, edited_at?}]}`. Anyone who can read the note reads and writes comments.

- `POST /notes/{id}/comments` with `{text, block_id?, quote?}` starts a thread on a block of the note (quoting up to 500 characters of it) or on the note. Text has 1–4,000 characters; a note has up to 500 threads.
- `POST /notes/{id}/comments/{thread}/replies` with `{text}` replies (up to 200 per thread), reopening a resolved thread.
- `PATCH /notes/{id}/comments/{thread}` with `{resolved}`: editors of the note, and the thread's author.
- `PATCH /notes/{id}/comments/{thread}/{comment}` with `{text}`: the comment's author changes it (`edited_at` is set); only people it newly mentions are emailed.
- `DELETE /notes/{id}/comments/{thread}/{comment}`: the comment's author; deleting the first comment deletes the thread.

Guests with an edit link use the same calls under `/api/v1/shared/comments…` (with the share cookie): they comment as "Guest", see members only as "Member" (`author` is `someone` but for their own comments), and their mentions email no one. View links get 403. `GET /mentions` lists comments mentioning the caller too (`comment: true`, with `thread` and `block`), beside notes whose text does.

People mentioned as `@person@example.com` who can open the note, and the thread's earlier participants, are emailed (when email is set up), never the author. Comments are deleted with their note, and a change signals open pages through `/api/v1/live`.

## Link previews

`GET /link-preview?url=…` returns `{url, title, description, site, image}` for a public web page, from its Open Graph tags or its title and description; signed-in members only. The server resolves the address itself and refuses private, loopback, link-local and other special networks, other ports than 80 and 443, and other schemes; it connects to the address it checked, checks each of up to 3 redirects the same way, reads up to 1 MB of HTML within 5 seconds, and keeps answers for a day.

**Database extras.** A number, rollup or formula property may have `format`: `percent` (0.25 shows as 25%) or `currency:{ISO code}` (`currency:EUR`); exports show values formatted. A rollup may combine a rollup or formula of the related database (up to three relations deep; a loop gives no value). Formulas have `related("Relation", "Property")`, the property's values across the linked records as a list, and `sum`, `average`, `first`, `last`, `unique` for lists. `PATCH /databases/{id}/rows/{row}` takes `rank` (a number, or `null`): the record's place in its board column, lower first; records without one follow in the order they were added. Replicas receive `rank`, and a record's page keeps its `record` link in desktop copies.

**One block at a time.** `PUT /notes/{id}/blocks/{block}` with `{markdown, base?}` changes one block, as the app does for a block embedded in another note: editors only; with `base` (the Markdown the change started from), a block that changed meanwhile answers 409 and is kept. The previous version stays in the note's history and open editors update. Published pages give each block `id="b-{block id}"`, and links to a block of another published note go to that anchor.

**Folding and link cards.** `PUT /notes/{id}/folding` with `{shared: true, folded: [block ids]}` keeps the note's folding in the note for everyone (`folded` on the note, blocks of the note only), and `{shared: false}` keeps it on each device again; editors only. Notes without `folded` fold per device. A block that is just a web address shows as a card; written `<address>` it stays a plain link. Share-link guests get previews from `GET /api/v1/shared/link-preview?url=…`, only for addresses that are a block of their note, and published pages show cards from previews the server already has, fetching missing ones in the background.

**Calendar feeds per workspace.** Besides `calendar-feed` (all of one's workspaces), `calendar-feed/{workspace id}` takes the same `GET`, `POST {journal?}`, `PUT {journal}` and `DELETE`, for a feed holding that workspace's reminders, `⏰` times and journal days only: an address to share with people outside it, showing what its maker can see. Reminders take `zone` (an IANA time zone such as `Europe/Rome`, which the app sends); a repeating reminder with one is written `DTSTART;TZID={zone}:{local time}` so calendar apps keep it at that local time across daylight-saving changes.

**Long recordings and speakers.** A recording larger than one transcription request (24 MiB) is sent in parts, cut where its format allows (WebM clusters, Ogg pages, WAV samples, MP3 frames; other formats must fit at once), up to the 60 MiB file limit; the job reports `part` and `parts` while it runs, and each part's times follow the earlier parts'. With a diarizing model (`MINERVA_ASR_MODEL` containing `diarize`, such as `gpt-4o-transcribe-diarize`), the request asks for `diarized_json` and segments carry `speaker`; labels are the provider's, per part. When notes are inserted, an action item's owner who is a member (their full name, or a first name only one member has) becomes an `@mention`.
